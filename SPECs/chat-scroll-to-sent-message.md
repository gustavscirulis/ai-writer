# Scroll a sent Chat message to the top

When the reader sends a message, the conversation scrolls so that message sits at the top of the Chat scroller. It stays there while the reply streams in below it, so the reader can read the reply as it arrives. Before this change, the scroller followed the bottom while the reply grew, which pushed the start of the reply out of view.

A spacer after the conversation contents makes the sent message reachable at the top even when the reply is short. The spacer's height is the sent message's scroll position, recorded once at send time, plus the viewport height, minus the content height. It's sized from content height only, because WebKit misreports descendant offsets while the slide runs. It shrinks as the reply grows and reaches 0 once the reply is taller than the viewport. After that the view doesn't move; the reader scrolls. The spacer sits outside the observed contents, so resizing it never feeds back into the ResizeObserver.

The anchor is set when the last message becomes a new user message. That covers Send, suggestions and queued sends. The anchor lasts until the next send, and `MessageList` remounts per note, so switching notes resets it. A thread that opens with history, including one that ends in a user message, starts at the bottom and keeps the old follow-at-bottom behaviour. Native smooth scrolling dropped frames because it shares the main thread with the start of the reply. Instead, the scroll position jumps, and the contents and spacer slide in from where they were on screen with a 240ms `translateY` animation on the `cubic-bezier(0.23, 1, 0.32, 1)` curve. The slide covers at most one viewport height. Sending again mid-slide cancels the running slide and starts the new one from the current position. The sent message only fades in (`data-pinned`), because the slide already moves it. Under reduced motion the jump is instant.

Validation: hook unit tests cover follow-at-bottom, spacer sizing, no auto-scroll while anchored, and no anchor on mount. A WebDriver run of the built app with the real CLI checks that `scrollTop` stays fixed while a long reply streams, that a second send re-anchors, and that a reloaded thread opens at the bottom.
